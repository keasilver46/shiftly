# 0002. 회원가입은 조직 단위로, 직원은 관리자가 등록

- 날짜: 2026-10-01
- 상태: 채택

## 배경

로그인 API 를 만들면서 회원가입을 어떻게 받을지 결정해야 했다.
일반적인 웹 서비스처럼 누구나 가입하는 모델이 이 서비스에 맞는지 의문이 있었다.

Shiftly 는 매장·소규모 팀의 근무표와 급여를 관리하는 서비스다. 직원의 소속 매장, 시급, 역할은
관리자가 결정하는 정보이고, 직원이 스스로 정할 수 없다. 데이터 모델도 이를 전제로 한다.
`users.organization_id` 는 NOT NULL 이고, `hourly_wage` 는 users 테이블에 있다.

## 선택지

1. **누구나 가입 (self-signup)**
   - 직원이 직접 가입한 뒤 "매장 A 소속" 을 선택하거나 초대 코드를 입력한다.
   - 장점: 일반적인 패턴이라 구현 사례가 많고, 사용자가 익숙하다.
   - 단점: 가입 시점에 소속이 없는 User 가 생겨 `organization_id` 가 nullable 이 되어야 한다.
     소속 승인, 시급 입력 등 관리자 개입이 결국 필요해서 흐름이 두 번 끊긴다.
     아무나 가입할 수 있어 스팸 계정 관리가 필요하다.

2. **조직 단위 가입 + 직원은 관리자가 등록 (B2B 모델)**
   - 관리자(점주)가 가입하면서 조직을 함께 만든다. 직원 계정은 관리자가 생성하고
     임시 비밀번호 또는 초대 링크로 첫 로그인을 하게 한다.
   - 장점: 모든 User 가 생성 시점부터 조직과 시급을 가진다. 데이터 모델과 일치한다.
     실제 근태 서비스(시프티, 알밤 등)가 쓰는 구조라 도메인 설명이 자연스럽다.
   - 단점: 직원 등록 UI 와 임시 비밀번호/초대 흐름을 만들어야 한다. MVP 범위가 늘어난다.

3. **가입 없음 (MVP 한정)**
   - 초기 데이터로 만든 데모 계정만 사용한다.
   - 장점: 구현 비용 0. 포트폴리오 열람자는 가입 없이 바로 체험하는 것이 오히려 낫다.
   - 단점: 실제 서비스로는 쓸 수 없다. 단독으로는 최종 답이 될 수 없다.

## 결정

**2번을 목표 구조로 하되, MVP 에서는 3번으로 시작한다.**

- MVP(현재): 회원가입 엔드포인트 없음. `POST /auth/demo-login` 과 local 프로파일의 초기 데이터로 대체.
- 2단계 "직원 관리": 관리자가 직원을 등록하는 `POST /admin/users`. 임시 비밀번호 발급,
  첫 로그인 시 비밀번호 변경 강제.
- 3단계: 관리자 가입 `POST /auth/signup`. 조직 + ADMIN User 를 한 트랜잭션에 생성.

1번을 택하지 않은 결정적 이유는 데이터 모델이다. 소속 없는 사용자를 허용하면
근무표·출퇴근·정산 모든 조회에 "소속 없음" 분기가 생긴다. 가입 흐름 하나를 위해
전체 도메인의 불변 조건(모든 사용자는 조직에 속한다)을 깨는 것은 비용이 더 크다.

## 결과

- `User.organization` 은 계속 `optional = false` 로 유지한다.
- `demo-login` 은 운영 환경에서 비활성화하거나 데모 전용 환경에서만 켠다. (배포 시 처리)
- 직원 등록 시 임시 비밀번호 전달 수단(이메일 발송 vs 관리자가 직접 전달)은
  2단계 구현 시 별도 ADR 로 결정한다.
